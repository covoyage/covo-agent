`tool_search` uses a cached in-memory BM25 index over available tool names, descriptions, local retrieval tags, nested parameter names/descriptions, and string enum/const capabilities. JSON schema structural keywords are not capabilities. Identifier components are searchable, including underscore-separated actions and camelCase parameters. Exact names take priority, with alphabetical tie-breaking. Retrieval is lexical, not multilingual semantic search: translate non-English intent into English capability keywords while preserving exact tool/action names, or configure suitable local tags.

English Snowball stemming (`github.com/kljensen/snowball v0.10.0`) adds a lower-weight lexical channel, such as `preference/preferences` and `reading/read`, without replacing original tokens. Only ASCII alphabetic words are stemmed; identifiers, digits and non-English tokens retain their original form. Keyword search also accepts prefixes of at least four Unicode characters in tool names/name components, not arbitrary description substrings. Two BM25 fields have independent document frequencies and length normalization: full metadata (raw/stem weights 0.35/0.1225) and deduplicated name/first-sentence/declared-search-term evidence (2/0.7). The primary contribution is scaled by its squared query-term coverage; overall coverage favors complete action/object matches. Non-exact per-word name bonuses also use squared coverage, preventing generic `find` or `mcp` terms from automatically beating more specific tools. Exact query names retain their priority. Both fields reuse cached documents. Exact `select:` and required `+word` constraints do not acquire stemming or semantic expansion.

Local static `ToolContract.RetrievalTerms` declarations add natural-language capability hints for filesystem, Git, shell, clarification and web capabilities. For example, reading a file also supports display/inspect/view vocabulary. A separate retrieval-only table covers memory, move and human handoff without declaring new permission contracts. `ApplyToolContracts` appends hints idempotently, without modifying model-visible descriptions/schemas, approval requirements or execution behavior. Only explicit `SearchTerms`, not execution/permission metadata, enter the primary search field. Unknown tools and concrete MCP identities do not inherit native hints by suffix. Contract lookups return independent hint slices. This is curated metadata, not a global synonym dictionary or inferred remote capabilities.

Natural-language query normalization removes common conversational words and ignores filename-like tokens and pure numbers in multiword queries, reducing incidental matches from concrete paths or line ranges. It does not understand general negation. A single underscore-separated identifier absent as a literal in the catalog requires evidence for every meaningful component in the same candidate, rather than matching only a generic action such as `create`. Literal schema actions such as `download_cancel`, exact names, and explicit `select:`/`+word` behavior remain supported. Empty results are still lexical no-matches, not proof that an arbitrary task cannot be performed.

The index caches immutable documents per tool. Unchanged native definitions are compared structurally without serializing/hashing the entire catalog; changed definitions alone are copied, encoded, and tokenized. Native schemas remain mutable, so cache hits still scan metadata, including in-place schema edits. Catalog changes rebuild aggregate postings/statistics from cached documents, and removed tools are evicted. This is incremental document reuse, not an O(1) registry-revision lookup or fully incremental posting updates.

Search with capability keywords, `select:Name1,Name2` for exact names, or `+word` to require a substring in the tool name only. Exact selection accepts a unique case-insensitive spelling but reports ambiguity instead of guessing; search, describe, and call use the same name resolution. Results contain full descriptions and parameter schemas. The default result limit is 10, capped at 50. Selection reports unavailable, ambiguous, and truncated entries. Counts exclude discovery helpers and policy-hidden tools, and no-match results include retry guidance.

Search, describe, and bridged calls share the model's active toolsets, availability checks, name allowlist, context/role policy, Plan-mode restrictions, and Cyber visibility. Only lean-mode declaration hiding is skipped for discovery: a long-tail tool can remain discoverable without appearing in the top-level tool list, but discovery does not bypass those policies. Policy is evaluated for each discovery call using its current context.

Both search and describe accept `max_output_bytes`: default 32,000, minimum 1,024, maximum 128,000 serialized JSON bytes. Schemas are never partially cut. Search removes whole lower-ranked declarations until the response fits, reporting `budget_limited` (some retained) or `output_budget_exceeded` (none retained), with `deferred` names, `required_bytes`, and `deferred_count`. Diagnostics can themselves be shortened or replaced by a bounded fallback. Describe a deferred tool with a budget at least its `required_bytes` to receive one complete declaration. A declaration beyond the hard maximum yields `schema_too_large`; do not repeat describe or call it with an unseen schema. Choose an alternative or an already directly visible interface. Byte limits are not exact provider token limits.

For long-tail tools, use `tool_search` then `tool_call` with the returned schema; a separate `tool_describe` is normally unnecessary. The bridge requires a matching full parameter contract in an actual search/describe result retained in the final model request, not merely in persistent session history. Missing/truncated declarations yield `schema_required`; changed parameters yield `schema_changed`. Refresh with search or describe and retry. Description-only changes do not invalidate a review. Reviews are per agent and rebuilt after each model call, including overflow retries. Discovery helpers cannot be invoked through the bridge. Tools already directly visible should be called by their own names; search does not inject declarations into the top-level tool list or grant execution permission. Bridged calls still use `InvokeTool`, including the target's hooks, validation and approval pipeline.

Connected MCP tools are discoverable individually as `mcp__<server>__<tool>`, including their descriptions and complete remote input schemas. Search and describe return a separate `source` object with the server, original tool name, and an opaque per-connection identifier; credentials and endpoints are not included. The identifier is not an authorization token. Metadata refresh updates discovery, removed/disconnected tools disappear, and replacing a connection invalidates prior reviews even if the tool name and parameters are unchanged. The catalog does not register these tools as top-level model declarations. Duplicate remote identities are omitted, and remote tools cannot shadow an existing registered tool.

Each MCP connection caches its immutable discovery snapshot. Warm discovery reuses it under a read lock, including while a remote call holds its execution read lock. Refresh invalidates the snapshot, replacement creates a new connection identity, and disconnect removes it. Internal production discovery avoids defensive JSON deep copies; the defensive-copy accessor remains separate.

The connection and parameters are rechecked immediately before sending the request, including after approval hooks; changes during approval fail without invoking the replacement. Discovery requires the generic `mcp` gate as well as concrete name, context, and availability filters; Plan mode inherits the `mcp` restriction. Calling `tool_call` with the generic `mcp` name and `action=call` is refused because reviewing the wrapper does not review a remote tool. Direct use of the `mcp` management/call interface remains supported under its existing policy. Standard MCP `inputSchema` and legacy `input_schema` are accepted, and numeric metadata/arguments retain JSON number precision. Servers' metadata and results remain untrusted.

Local/CDP `screenshot` writes a private PNG and returns its actual path, dimensions and byte count; use `read` to inspect it. `full_page=true` captures the full document. Images are limited to 4 MiB and removed when the extension is disposed. `vision` uses the configured auxiliary vision provider and returns errors, not placeholder success, if analysis fails. `console` returns up to 200 bounded, secret-filtered messages per attached tab. `cdp` executes real page-scoped diagnostic methods; browser-global commands, cookie extraction, arbitrary tab creation and CDP navigation are not exposed. `status` reports session/dialog state, `wait` waits for a visible CSS selector with the command timeout, and `close` releases all owned pages. Set `BROWSER_PROFILE_DIR` to opt into a dedicated persistent local profile. The directory must be empty or initialized by covo-agent, private (0700 on Unix), and not a symlink. In Cyber mode, the built-in browser passively records traffic only while `request_intake` is explicitly enabled for the exact request host. The scope is checked before capture and again before saving. Observation uses the tool instance's own CDP target and adds no target HTTP requests; it does not restrict the browser's own destinations or replace browser approval/network policy. Local Chrome is integration-tested; other CDP backends require compatible Network events, and unsupported or failed observation is logged explicitly. Separate popup targets, independent workers, and requests issued before observation starts are not guaranteed. Missing headers, bodies, redirects, response read failures, queue loss, and closure with unfinished work are not treated as complete captures.

Browser capture has 128 in-flight records, 64 queued completions, 2,000-byte headers, 4,000-byte request bodies, an 8,000-byte persisted response ceiling, and bounded CDP buffers. Common credential/PII query/body fields and authentication headers are forcibly filtered before persistence, regardless of `COVO_REDACT_SECRETS`. Request bodies are accepted only as bounded unambiguous JSON or URL-encoded forms; only complete bounded JSON response bodies are saved. Unknown, duplicate-key, malformed, oversized, and incomplete bodies remain omitted or marked incomplete. Filtering is conservative, not an application-specific secret guarantee. Browser evidence stores source/session/request IDs but never infers identity labels from cookies or tokens; label chosen evidence explicitly. Normal role, replay completeness, scope, and request-budget gates still apply.

Cyber HTTP evidence storage is capped at 500 exchanges. Enabled `request_intake` groups exact-origin HTTP operations using conservative numeric/canonical-UUID path templates and nested JSON field shapes (depth 8, 128 visited nodes). Encoded path variants remain distinct. JSON-RPC methods and common query/body dispatch fields remain distinct. Grouping never changes the stored URL, replay target, or authorization scope.

In-scope, non-replay captures accumulate at most 500 private request observations, deduplicated by operation, identity labels, and sanitized parameter observations. This conservative filter is not application-specific secret classification. `web_context` returns at most 20 observations with completeness/truncation flags. Labels and observed IDs do not prove ownership, privileges, or vulnerabilities. Evidence references remain retained; there is no automatic observation garbage collection, and capacity exhaustion fails explicitly.

New observations or changed labels requeue existing reviews of the same operation using a durable context digest. Pending updates coalesce; updates during a running review schedule a follow-up after completion. Each job has at most three automatic attempts, including crash recovery, then becomes `blocked` for parent review. Dispatch reads the latest context and rechecks enabled exact hosts. Automatic verifiers keep their original exchange ID and exact path, cannot retrieve another observation's raw exchange, submit forms, change identities, or write findings. Cross-account signals are review leads, not automatic authorization for differential testing. Ledger coordination remains process-local.

These API checks are not filesystem sandboxing; scanner and shell access remain subject to existing workspace/approval policy.

`cyber_storage` previews expired full-output spills and Markdown/CSV/SARIF exports (30-day default). Apply requires the unchanged preview revision and the parent role. Finding/evidence ledgers are never deleted. Referenced files, unsafe entries, active engagements, pending/running intake, and running retests are protected. Corrupt/oversized ledgers abort cleanup. Cleanup coordination is process-local; do not run it alongside another process writing the same catalog. Interrupted retests remain protective until their terminal state is explicitly resolved; session image assets are outside this cleanup scope.

`scan_profile` updates require the revision from a preceding read. Hosts, depth, and whitebox settings are validated before one atomic write; stale revisions and competing writers fail closed. Participating profile writers use a persistent OS lock file.

Configuration saves use a loaded-file digest to reject intervening edits, preserve unknown YAML keys/comments and unchanged environment placeholders, and publish through a synced temporary file. Global and named-profile saves share a persistent OS lock. Newly constructed configurations have no loaded revision; they remain explicit replacement inputs for known settings. Session startup compares ordinary tables with the native schema and applies safe additions transactionally; missing identity/required data fail startup. Existing fields and extension columns are untouched, and FTS keeps its dedicated migration.

Binary updates serialize participating processes and persist a bounded recovery journal before renaming executables. Version checks and update attempts recover pending installations using confined paths and matching old/new SHA-256 identities; invalid or contradictory evidence stops recovery. Backups are kept through activation verification and removed only when the expected new binary is present. This verifies file identity, not runtime health or publisher authenticity. Filesystem changes by nonparticipating processes are not prevented by these locks.

Approval decisions distinguish final denial from an interactive approval request. Final command/policy denials cannot fall through to a checker, and automatic command approval never skips an explicit checker. Execution and file-mutation tools share one approval classification, including local sandbox commands, MCP connections/calls, external agents, scripts, and deletion aliases. Explicit path-policy `ask` requires approval even for read-only tools or automatic TUI approval modes. Without an approval requester, operations requiring approval fail closed. Each production agent has an independent policy snapshot; invalid policy loading fails initialization. Interactive approval requests are serialized and callbacks are bound to their originating request, so cancellation cannot approve a later call.

File safety and read-only checks cover every structured `apply_patch` add/update/delete/move target, both endpoints of `move`, and write/append/delete aliases. Patch paths default to the agent workspace. New paths resolve through existing ancestors, including symbolic links, before workspace checks. These are pre-execution checks, not protection against a separate process changing filesystem links after approval.

ACP WebSocket relay defaults to `127.0.0.1:17891`. A non-loopback listener requires `COVO_ACP_WS_TOKEN`; clients send `Authorization: Bearer <token>`. Browser origins must match the requested host, and tokenless loopback connections require a loopback Host. The relay limits concurrent connections to 16 and inbound messages to 1 MiB by default. Use TLS termination or an authenticated tunnel for remote access: bearer authentication does not encrypt plain WebSocket traffic. ACP subprocesses also use OS child-command preparation.

The API chat-completions endpoint correlates replies using per-request IDs, independently of session history. An explicit `X-Session-Id` preserves the session; concurrent requests for that session receive HTTP 409. Without that header each request gets an isolated session. Gateway replies carry the request ID; custom message callbacks must preserve `IncomingMessage.RequestID` in `OutgoingMessage.RequestID`. Late replies cannot satisfy a newer request. Waiting respects HTTP request cancellation and defaults to two minutes; an unavailable pipeline returns 503 and a missing reply returns 504, never an empty successful completion. Timeout cancels waiting, not necessarily backend execution.

Hub installation requires a valid live or cached registry index containing the skill. Declared SHA-256 pins must match; an index entry without a pin remains supported but does not provide pinned integrity. Index and manifest reads are bounded to 2 MiB and 1 MiB respectively. The binary installer requires a SHA-256 tool and exactly one valid checksum entry from the release checksum file; missing verification never silently proceeds. Same-origin checksums detect content mismatch, not compromise of the release publisher.

Release builds use the published `covonaut v1.1.6` dependency without absolute local replacements. Local sibling development can use an ignored `go.work`; use `GOWORK=off` for release/CI verification.

Native tool capability declarations carry read/write/execute classification and mutation parameter names alongside the tool, so renamed declared tools retain approval and workspace checks. Write/execute/conditional declarations remain serial barriers; undeclared tools retain legacy classifications. Unknown conditional declarations require approval. These are trusted local registration declarations, not a certification of remote implementation behavior.

File mutation locks canonicalize the longest existing ancestor, including missing leaves below symbolic-link aliases. Multi-target patches lock deduplicated canonical paths in sorted order and revalidate while locked; moves lock both endpoints. Locks serialize participating operations within one process only. A patch is not a rollback transaction, and external processes can still race filesystem changes.

Skill proposal application records a base digest and durable application plan before publishing. Changed skill content blocks application rather than overwriting intervening edits. Startup retries pending publication and final bookkeeping; deletion archives the whole bounded package. Corrupt proposal state or recovery conflicts fail initialization. New proposals capture their base at creation; legacy proposals without a base capture it at application. This protects normal retry/crash recovery, not concurrent writers in another process. Dream and consolidation remain advisory.

Full compaction preserves the latest user's real image blocks. Earlier supported data-URL images become content-addressed session assets; retained references are revalidated for directory confinement, regular-file status, MIME type, digest, and an 8 MiB per-image limit, with at most 16 references per compaction. Asset-root configuration is trusted; candidate file links are rejected. Remote historical URLs are not fetched during compaction. Unreferenced session assets are not automatically garbage-collected.

Declared file-read results carry `details.source_summary` when their result envelope can be instrumented. Execution success is separate from completeness: `yes`, `window`, `no`, or `unknown`; observed truncation reasons and output line/byte counts come from actual tool details, never textual success markers. Unobserved media/directory/custom reads remain unknown, and source role remains unknown rather than inferred from paths. Audit records and microcompaction retain these facts. They describe the read output before later context trimming, not an immutable snapshot of the file or a guarantee that all original content remains in context.

Local sandbox commands, interactive bash, background processes, cron pre-run commands, native scans, local MCP servers, and external-agent launches share OS child-command preparation. Explicitly requested CLI sandboxes fail startup when unavailable. Active network-restricted profiles use a trusted, absolute, root-owned launcher (`sandbox-exec` on macOS, `unshare` on Linux), reject writable launcher paths and dynamic-loader injection variables, and probe support before execution. This is child network denial, not an allowed-host firewall; default/workspace profiles do not restrict scanner destinations at the OS level. Other runtime-managed processes and remote/container backends are not covered by this local launch hook.

MCP requests reject pre-cancelled contexts. Stdio and HTTP transports send bounded best-effort `notifications/cancelled` messages for cancelled or timed-out requests (except initialization); local pending requests are cleaned up, and late stdio responses are ignored safely. A blocked stdio write closes the connection to unblock callers. Successfully initialized stdio servers remain alive until disconnect, rather than depending on the initialization context's lifetime.

`sessions_fork` requires `task` and captures history from runtime state, not model-supplied `history` or `depth`. Snapshots retain completed tool call/result pairs, drop the unfinished trailing tool batch and parent system messages, and clear historical approval metadata. Child capabilities and policy settings are inherited independently from history; toolsets stay within the parent's configured restriction. Live process/connection handles and existing approval decisions are not inherited.

External skills are audited as packages during loading and before Hub manifest replacement. Package ignore files cannot hide support scripts or Python bytecode. Text decoding supports UTF-8 and BOM-tagged UTF-16; linked roots, unreadable or unsupported artifacts, and exhausted read/traversal budgets cannot produce an accepted complete audit. Version-control metadata is excluded and makes coverage incomplete. Embedded trust requires matching the whole bundled package, not a source label or filename. Pattern hits are candidate risks, not proof of malicious intent; normal credential lookup alone is not a high-severity finding. This is a load/install gate, not immutable execution-time verification. Hub still downloads only the registry's `SKILL.md`, not arbitrary archives.

`mcp_audit` accepts only `server` and calls `tools/list`, never `tools/call` or process creation. It preserves raw definitions, scans descriptions and decoded schema text, and compares against the connection baseline (refresh does not reset it). Empty, malformed, oversized, failed, or cancelled results do not certify safety. Definition drift is advisory and requires review; it does not automatically block subsequent MCP calls. Metadata completeness says nothing about remote implementation behavior, resources, or prompts. Returned definitions remain untrusted input.

The native `scan` recipe `ai-infra-guard` expects an independently installed Cobra CLI binary named `ai-infra-guard` on PATH and explicit absolute local rules directories in `options.fingerprints` and `options.advisories`. It uses one HTTP(S) target, a fixed request timeout and rate limit, and rejects extra flags, secondary targets, proxy options, local scanning, and AI-token options. Existing Cyber target authorization and child-process preparation apply, but scanner redirects and rule behavior are not an OS allowed-host firewall. Output remains observations/advisory candidates, especially when versions are unknown; confirmed findings still require evidence. No external rule database is bundled. Based on Tencent Zhuque Lab AI-Infra-Guard: https://github.com/Tencent/AI-Infra-Guard (external project attribution; native adapter implementation).
